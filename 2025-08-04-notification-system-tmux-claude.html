Notification System for Tmux and Claude Code

2025-08-04 · DevOps

ON THIS PAGE

Introduction¶

As a lot of technical people nowadays, I am using Claude Code on a daily basis. In fact, I am using a lot of parallel Claude Code sessions, either to work on the same project but different features, or to work in parallel on different projects.

Designing a proper workflow is essential in order to keep track of everything. There are some orchestrators such as vibe-kanban and some nice webui such as claudecodeui or Claudia. My opinion is that these web UI are interesting mostly to have an overview of the sessions rather than orchestrate it. They are also helpful for high level tasks or tasks that are not too technical and for which the current state-of-the-art LLM and agentic workflow can reasonably perform well.

However, my experience is that Claude and all LLMs are not to be trusted in most cases to perform the job I am doing. No matter how much effort is put in the prompt, in the definition of the agents, etc. there is always a moment where, if not fully supervised, something will go wrong unless I move step by step.

Because of that, these orchestrators or web UI are not suitable for my daily workflow because I need to be in a terminal all the time and using these web UI is often a friction that makes me lose too much time. Therefore, I decided to design my own notification mechanism for Claude Code with some requirements:

  1. It must work on MacOS and Linux with minimal modifications,
  2. It must work with Claude-Code but also any other terminal-based agents such as Codex or Gemini CLI and the next best tool that will be available next week,
  3. The notifications must have the possibility to be forwarded to many clients (e.g. my phone, a light bulb controlled by Home Assistant for a visual feedback).
  4. On my machine, the notification must be native and when clicking on it, it must bring me to where the session of the tool is immediately.
  5. My environment is specific: I use ghostty with the dropdown mode, but all my terminal sessions are using tmux. There is no alternative. I have sessions (e.g. Work), windows (one per project/features) and usually 1 to 4 panes per window.
  6. I need to keep the possibility to create additional components in the future such as a web UI with all the notifications, some event DB for the notifications, etc.
  7. I want to build around Claude-code and not with Claude-code. As a result, I expect to be able to have Claude-code using the notification system that we will develop here. This is probably the most exciting use-case because it then because possible to have several claude-instance communicating with each other (spoiler alert, this is not going to end well!).

The components that I have chosen because I already use most of them personally:

  1. The trigger: Claude hooks
  2. The orchestrator: n8n
  3. The notification center: gotify
  4. The local script executor: webhook (https://github.com/adnanh/webhook)
  5. The actions:
    1. notifier script, with terminal-notifier in my case
    2. ghostty + tmux manipulator: bring ghostty in the forefront and move to the corresponding tmux location.

The Flow¶

Let’s briefly discuss the flow:

  1. A claude-code session started in a tmux pane (e.g. 1:0.1) is done or needs my input.
  2. A claude hook is triggered which calls a n8n workflow.
  3. The n8n send a message to an instance of gotify and to a local instance of webhook.
  4. Gotify notify all the registered clients and at the same time, webhook triggers a terminal-notifier.
  5. If clicked on, the notification call another webhook from the local webhook server that execute the script to shows the original claude-code session in its tmux pane.

An example of system notification. If I click on Show, it will brings me to the correct tmux location.

Why not using n8n alone instead of gotify?

While technically possible and probably easier to achieve notifications on specific applications such as Telegram, I wanted to decouple the orchestrator from the notification mechanism. Gotify is my messaging center for many different applications and it is actually hosted on a server and on the machine where claude-code is started. Gotify also has the concepts of users, applications and clients which offer more flexibility than n8n to manage notifications properly.

Why not using n8n to execute some script on the host?

This would work if n8n was started on the same machine as where claude-code runs which is not my case. My n8n instance is hosted, as Gotify, on a different server and it used for different machines. Separating the orchestrator from the executor is still a good idea regardless and it offers the possibility to extend our notification system to receive notifications from different machines (e.g. a remote server) and execute actions there.

Warning

To make it easy for people to try it, I will consider that all components are started on the same machine and I will provide the instructions for MacOS.

Preparing tmux¶

What triggers a notification is a claude hook on the event Stop and Notification.

Because I assume claude-code starts in a tmux pane, it is important to have the information about that tmux pane available to claude-code for the hook to send that information.

To do so automatically, add this to your .zshrc: 

1
2
3
4
5
6
# Automatically set these variables for new processes in tmux
if [ -n "$TMUX" ] && [ -z "$WS_TMUX_LOCATION" ]; then
  export WS_TMUX_LOCATION=$(tmux display-message -p '#{session_name}:#{window_index}.#{pane_index}')
  export WS_TMUX_SESSION_NAME=$(tmux display-message -p '#{session_name}')
  export WS_TMUX_WINDOW_NAME=$(tmux display-message -p '#{window_name}')
fi

This will export environment variables at the moment the tmux pane is created. Therefore, when any process is started, it will have these environment variables available.

To check that it worked, reload zsh and run: 

1
echo $WS_TMUX_LOCATION $WS_TMUX_SESSION_NAME $WS_TMUX_WINDOW_NAME

You should see something like: 

1
1:0.1 1 node # content varies depending on your tmux session and window name

Webhooks Scripts¶

We will create two scripts:

  1. ghostty-notify-wrapper.sh: generates the notification using terminal-notifier based on contextual information.
  2. go-tmux.sh : takes a tmux location and open the ghostty on it.

Both scripts will be registered as webhook and the notification generated by the first one will trigger the second one. Because webhook has been started with the flag autoreload, we do not have to reload it when we add new hooks or modify the underlying scripts. Also, because the parts of the system that are specifically tailored for my workspace (ghostty, terminal-notifier) are isolated in these small scripts, it is really easy to adapt it for another environment.

Note

If you are to modify these scripts, you must use absolute path for all the executable such as terminal-notify or tmux.

#!/bin/zsh

# Log ALL output
LOG="/tmp/tmux-notifier.log"
exec >> $LOG 2>&1

echo "=== CLICK EVENT: $(date) ==="
echo "PWD: $(pwd)"
echo "SHELL: $SHELL"
echo "PATH: $PATH"
echo "USER: $USER"
echo "LOCATION: $1"

# Source zsh environment
source "$HOME/.zshenv" 2>/dev/null
source "$HOME/.zshrc" 2>/dev/null

export PATH="/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin:$HOME/bin"

echo "FINAL PATH: $PATH"

TMUX=$(whence -p tmux || echo "/usr/local/bin/tmux")
echo "TMUX binary: $TMUX"

if [[ ! -x "$TMUX" ]]; then
  echo "ERROR: tmux not found or not executable at $TMUX"
  exit 1
fi

LOCATION="$1"

if [[ -z "$LOCATION" ]]; then
  echo "ERROR: No location provided"
  exit 1
fi

if [[ "$LOCATION" =~ ^([^:]+):([0-9]+)(\.([0-9]+))?$ ]]; then
  SESSION="${match[1]}"
  WINDOW="${match[2]}"
  PANE="${match[4]}"
else
  echo "ERROR: Invalid format: $LOCATION"
  exit 1
fi

echo "Switching to: session=$SESSION, window=$WINDOW, pane=$PANE"

# Run tmux commands
"$TMUX" select-window -t "$SESSION:$WINDOW"
if [[ $? -ne 0 ]]; then
  echo "ERROR: tmux select-window failed"
else
  echo "OK: select-window succeeded"
fi

if [[ -n "$PANE" ]]; then
  "$TMUX" select-pane -t "$SESSION:$WINDOW.$PANE"
  if [[ $? -ne 0 ]]; then
    echo "WARNING: select-pane failed"
  else
    echo "OK: select-pane succeeded"
  fi
fi

# Try to focus Ghostty
osascript -e 'tell application "Ghostty" to activate'
if [[ $? -eq 0 ]]; then
  echo "OK: osascript ran successfully"
else
  echo "ERROR: osascript failed with code $?"
fi

echo "=== END ==="

Claude Hooks¶

Claude hooks have a payload that we want to preserve as we can leverage it for additional information for the notifications such as the hook type, cwd, or session id. We want to add the environment variables to the payload to be forwarded to n8n webhook.

To do that, we just have to use jq and pipe it to a curl call to the n8n webhook that triggers our workflow.

Here is an example on how to add new fields to an existing payload: 

1
echo '{"original": "payload"}' | jq --arg tmux_location "$WS_TMUX_LOCATION" --arg tmux_session_name "$WS_TMUX_SESSION_NAME" --arg tmux_window_name "$WS_TMUX_WINDOW_NAME" '. + {tmux_location: $tmux_location, tmux_session_name: $tmux_session_name, tmux_window_name: $tmux_window_name}'

This should output the following:

  "original": "payload",
  "tmux_location": "0:1.2",
  "tmux_session_name": "Work",
  "tmux_window_name": "window name"
}

Therefore, with the following command, we forward the enhanced payload to a n8n webhook called claude-code-notification:

1

n8n Workflow¶

The workflow is really simple:

  1. One trigger: a webhook receiving claude-code hook’s forwarded payload
  2. A node to remap and transformed the fields from the payload
  3. A HTTP request to Gotify and a HTTP request to the webhook server

I will provide the full JSON of the workflow at the end but because it is relatively easy to configure, it might be faster to actually do it manually.

Conclusion¶

This notification system provides a powerful way to manage multiple Claude Code sessions efficiently. By leveraging tmux, n8n, Gotify, and native macOS notifications, we’ve created a system that:

  • Provides instant notifications when Claude Code needs attention
  • Allows one-click navigation to the correct tmux pane
  • Supports multiple notification channels
  • Builds around Claude Code without modifying it
  • Can be extended to other terminal-based tools

What’s Next?¶

  • Web UI with tmux controls, showing the layout, notifications per windows and panes and allow to move by clicking on button (why not touch screen or macropad shortcuts)
  • Allowing Claude-code to interact with tmux panes and then allowing Claude-code to control and discuss with other claude-code instances
  • Integration with more notification services (Home Assistant, Discord, etc.)
  • Event database for tracking and analyzing notification patterns
  • Support for other terminal multiplexers beyond tmux
